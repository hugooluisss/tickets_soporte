# Design

## Context

Backend layering is controller → service → repository per resource (`openspec/changes/add-ticket-support-system/design.md`). `TicketsService.create(input, creatorId)`/`update(id, input)` (`backend/src/tickets/tickets.service.ts`) are the only places tickets are written today; `TicketsController`/`ProjectsController` are both `@UseGuards(JwtAuthGuard)` at the controller level (`backend/src/tickets/tickets.controller.ts`, `backend/src/projects/projects.controller.ts`). `Ticket.createdBy` (`backend/src/tickets/ticket.entity.ts`) is `@ManyToOne(() => User, { onDelete: 'RESTRICT' })`, currently required; `TicketsRepository` already `leftJoinAndSelect`s it (not an inner join), and the frontend `Ticket.createdBy?: User` (`frontend/src/app/features/models.ts`) is already optional — so nullability plumbs through cleanly on both sides without further changes to those two spots. No email or webhook sending exists anywhere in this codebase today; no `@nestjs/throttler`, no `nodemailer`.

## Goals / Non-Goals

**Goals:**
- Unauthenticated, project-scoped ticket intake with basic abuse protection.
- A per-project webhook fired on ticket creation, and a per-ticket-update reporter email — both fire-and-forget, never blocking or failing the request that triggered them.
- Reuse `TicketsService`/`ProjectsService` for the actual create/update logic rather than duplicating validation in a parallel "public" code path.

**Non-Goals:**
- No webhook signing/secret, no retry queue, no delivery-status tracking — a single best-effort POST, logged on failure (per user decision).
- No email templating system or transactional-email provider integration (e.g. SendGrid/Mailgun API) — plain SMTP via `nodemailer`, matching this deployment's likely constraints (a single internal-tool app, not a marketing/email platform).
- No notification preferences, unsubscribe, or digest batching — every update to a reporter-having ticket sends one email (per user decision: "cualquier actualización").
- No change to internal-ticket-creation behavior, guards, or contracts.

## Decisions

- **`created_by_id` becomes nullable; three new nullable `tickets` columns**: `reporter_name` (varchar 150), `reporter_email` (varchar 255), `reporter_location` (varchar 255). Migration `backend/src/database/migrations/1730000005000-AddTicketReporterFields.ts` (raw SQL `ALTER TABLE`, matching this project's migration style): `MODIFY COLUMN created_by_id char(36) NULL`, plus three `ADD COLUMN` statements. No new index needed (reporter fields aren't filtered/joined on in this change).
  - The internal-vs-public invariant (`created_by_id` XOR `reporter_name`+`reporter_email`) is checked in `TicketsService`, not the DB — consistent with `validateReferences`'s existing style of app-layer validation for cross-field rules.
- **New `backend/src/public-tickets/` module** (`PublicTicketsController`, thin — no separate service): `GET /api/public/projects/:projectId` calls `ProjectsService.findById` and returns only `{ id, name }` (never the full `Project`, which includes ticket counts and, after this change, the webhook URL — an internal detail). `POST /api/public/projects/:projectId/tickets` calls `TicketsService.createPublic(projectId, { reporterName, reporterEmail, reporterLocation, title, description, kind })`, a new method alongside the existing `create()`, so the "public" shape (no `creatorId`, mandatory reporter fields, no priority/status/assignee/category input) is explicit at the type level rather than an authenticated `create()` called with an omitted `creatorId`.
  - Alternative considered: reuse `TicketsController`'s existing `POST /tickets` with an optional-auth guard. Rejected — mixing "sometimes authenticated, sometimes not" on one endpoint blurs the DTO contract (what's required changes based on auth state) and makes the rate-limit/guard story harder to reason about than two small, single-purpose endpoints.
- **Rate limiting via `@nestjs/throttler`**, applied with `@UseGuards(ThrottlerGuard)` + `@Throttle(...)` only on `PublicTicketsController` (module-local `ThrottlerModule.forRoot(...)` import scoped to that module, not a global `APP_GUARD`), so existing authenticated endpoints are unaffected. Limit: a small fixed window (e.g. 5 requests/minute per IP) — generous enough for a real visitor filling the form (including a mis-click retry), tight enough to blunt casual scripted abuse. Exact numbers are a config value, not a hard requirement — tune later without a spec change.
- **Webhook dispatch**: a new `backend/src/notifications/webhook-notifier.service.ts`, called from `TicketsService.create()`/`createPublic()` after the ticket is persisted, given the project's `webhookUrl` (loaded via `ProjectsRepository`, no extra query since `TicketsService` already validates `projectId` against `ProjectsRepository` in `validateReferences`). Implementation: `fetch(url, { method: 'POST', body: JSON.stringify(payload) }).catch(err => this.logger.error(...))` — **not awaited** by the caller (fire-and-forget in the literal sense), so a slow/unreachable endpoint can never delay the ticket-creation response, satisfying `project-webhooks/spec.md`'s "does not require the recipient to be reachable synchronously" requirement. Payload: `{ ticketId, title, projectId, projectName, kind, reporterName?, reporterEmail? }` — enough for a receiving system to look the ticket up or act on it, without dumping the full internal `Ticket` shape.
- **Email dispatch**: a new `backend/src/notifications/email-notifier.service.ts` wrapping `nodemailer`, called from `TicketsService.update()` after a successful update, only when the updated ticket has `reporterEmail` set. Same fire-and-forget pattern as the webhook (not awaited, errors caught and logged) — satisfies `ticket-email-notifications/spec.md`'s "does not block the update response" requirement. `nodemailer` transport configured from new env vars (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`), added to `backend/.env.example` with placeholder values — actual delivery requires the operator to supply real SMTP credentials (out of scope to provision here, same as `JWT_SECRET`/`DB_PASSWORD` already being placeholders in `.env.example`).
  - Ticket creation deliberately does **not** send this email (see `ticket-email-notifications/spec.md`'s "creation does not itself trigger" requirement) — a public submitter already gets on-screen confirmation from `public-ticket-submission`; the email channel is for staying informed after they've left the page.
- **`notifications` module has no dependency on `public-tickets` or vice versa** — both `TicketsService.create()`/`createPublic()`/`update()` call into `WebhookNotifierService`/`EmailNotifierService` directly (injected), keeping notification concerns orthogonal to how a ticket was created. This also means an *internal* staff-created ticket for a project with a webhook still fires that webhook (per `project-webhooks/spec.md`'s scenario explicitly covering "public or internal"), and any ticket update — internal or public in origin — emails its reporter if it has one, since the trigger is "does this ticket have a reporter email," not "was this ticket publicly submitted."
- **Admin project form gets a `webhookUrl` field**: `CreateProjectDto`/`UpdateProjectDto` gain `@IsOptional() @IsUrl() webhookUrl?: string`, `ProjectsService.create`/`update` pass it through, `frontend/src/app/features/projects/project-form/` gets one more `app-form-field` (type `url`), and `frontend/src/app/features/projects/project-list/` needs no change (webhook URL is a configuration detail, not a list-view column, consistent with `description` also not being a dedicated list column beyond its existing truncated display).

## Risks / Trade-offs

- **Fire-and-forget webhook/email means silent failure from the requester's point of view** — a broken SMTP config or dead webhook URL fails quietly (log-only) → mitigation: this is the user's explicit choice (no retry queue, no delivery tracking) for this iteration; backend logs are the only current visibility, documented here so it's a known limitation, not a surprise.
- **No real SMTP credentials exist in this dev environment** — email sending will fail (and log) in dev/test unless an operator supplies working `SMTP_*` env vars → mitigation: not a blocker for this change (the code path is fire-and-forget and logs rather than throwing), but verification tasks should confirm the *logged failure* path works correctly even without real credentials, since that's what local/dev verification will actually exercise.
- **A public ticket's `reporter_email` is unauthenticated, unverified input** — anyone can type any email address into the public form, so update emails could go to an address the visitor doesn't control → mitigation: none added in this change (no email verification was in scope per the user's decision); acceptable for an internal tool's client-intake use case, revisit if abuse is observed.
- **`@IsUrl()` on `webhookUrl` rejects non-URL strings but doesn't verify the endpoint is a legitimate webhook receiver** — an admin could point it at an arbitrary internal or external URL → mitigation: out of scope (this is an admin-only, trusted-input field, same trust level as every other admin-only field in this app).

## Migration Plan

1. Backend: migration for `tickets` (nullable `created_by_id`, new reporter columns) and `projects` (`webhook_url`); entity updates.
2. Backend: `TicketsService.createPublic()`, `public-tickets` module (controller + `@nestjs/throttler` wiring).
3. Backend: `notifications` module (`WebhookNotifierService`, `EmailNotifierService`), wired into `TicketsService.create()`/`createPublic()`/`update()`; `nodemailer` dependency + `.env.example` additions.
4. Backend: `webhookUrl` on `CreateProjectDto`/`UpdateProjectDto`/`ProjectsService`.
5. Frontend: public route + submission form + confirmation state; admin project-form webhook field.
6. Verify: public submission end-to-end (valid/invalid project, validation errors, rate limit), webhook fires (a local HTTP listener or logging-only check given no real external endpoint in dev), update email attempt is logged (given no real SMTP in dev, confirm the failure path logs correctly rather than throwing/blocking the update response).

No rollback complexity beyond a plain git revert — additive columns, no destructive migration.
